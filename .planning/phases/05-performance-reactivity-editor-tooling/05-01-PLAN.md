<objective>
Replace `WatchAsync<T>`'s synchronous, per-`Set()` notification with a per-frame batched notification that coalesces to the latest value: many `Set()`s for the same key in one frame deliver exactly one update carrying the final value (WATCH-01). Also close the two deferred Phase-03 regression tests that live in this same `Set()`/watcher domain — CR-01 (the lenient coercion-failure warning must not leak the offending value; code already fixed, invariant currently untested) and WR-05 (a schema-coerced `Set` must reach a `WatchAsync<T>` subscriber of the schema type).

Purpose: today `DSMWatcher.Notify` writes to every subscriber channel synchronously on the thread that called `Set()`, so a hot loop that calls `Set("hp", ...)` 200 times in a frame wakes each subscriber 200 times that frame — wasteful and bursty. Batching to one latest-value notification per key per frame matches how a UI/consumer actually wants to observe state, with no extra allocation per intermediate value.

Output: a batched `DSMWatcher` (per-key pending buffer + dirty-flag/schedule-once flush on the PlayerLoop + an `internal Flush()` for deterministic testing), an unchanged `DSMSlot.Set` call site, a new EditMode `DSMWatcherBatchingTests`, and two added regression tests in `DSMSchemaValidationTests` closing CR-01/WR-05.
</objective>

## Phase Goal (MVP)

**As a** game developer subscribing to save-state changes via `WatchAsync<T>` to drive UI, **I want** many rapid `Set()`s of the same key within a frame to notify me only once with the final value, **so that** my UI updates once per frame instead of thrashing on every intermediate write. MVP slice: this is one cohesive runtime vertical — `Set()` buffers the latest value, the frame boundary flushes it once, and the subscriber receives exactly one coalesced update — delivered end-to-end with the current-value replay preserved.
