<objective>
Give every save file an explicit SaveVersion inside a { version, data } envelope (MIGR-01), migrate an out-of-date slot forward with small composable per-step transforms via IDSMMigration + DSMMigrationRunner (MIGR-02), do it lazily on load and write the upgraded result back immediately — never a bulk startup pass (MIGR-03), and lock the behavior with a TestFixtures/ set of versioned sample saves plus regression tests (TEST-06).

Purpose: today a slot file is a flat `{ key: value }` JSON blob with no version, so there is no safe way to evolve the save shape — a renamed key would be silently reseeded to its default and the old value lost. This phase wraps the payload in a versioned envelope, runs a per-slot migration chain only when that slot is loaded, and persists the migrated envelope back, so old saves upgrade correctly and losslessly on first touch.

Output: three new Runtime files (DSMSaveEnvelope, IDSMMigration, DSMMigrationRunner + DSMSaveVersionException), envelope-aware serialize/deserialize wiring through DSMSerializer/DSMSlot with a gate-safe load-time write-back, a static migration registry on DSM threaded through DSMSlotManager, and an EditMode DSMMigrationTests fixture backed by a committed TestFixtures/ directory.
</objective>

## Phase Goal (MVP)

**As a** game developer shipping updates to a game that already has players' saves on disk, **I want** an old save to carry an explicit version and migrate forward correctly and losslessly the first time it is loaded — without a bulk startup migration pass — **so that** I can evolve my save shape (rename/remove/add keys) across releases without corrupting or discarding existing player data.

Note: derived from the ROADMAP Phase 4 `**Goal:**` line. DSM is a library, so its "user" is the integrating developer; the ROADMAP goal was not authored in user-story form and is restated here without changing scope. MVP framing: this phase is one cohesive vertical slice — write a lower-version save, load it, detect the version, apply the stepwise migration chain, hand the consumer the upgraded data, and re-persist it in upgraded form — delivered end-to-end rather than as independent horizontal layers.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| on-disk save file -> DSMSlot.Load/LoadAsync | Attacker- or corruption-controlled bytes (version field + payload) are parsed and drive the migration path |
| game code -> DSM.RegisterMigration / DSMMigrationRunner | Developer-supplied migration objects mutate the payload JObject during load |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Tampering / Data Loss | Migration write-back on an encrypted slot | high | mitigate | The load-time write-back reuses the SAME encrypt-aware atomic write core as Save (`WriteJsonToDisk`/`WriteJsonToDiskAsync` retain the `if (_config.Encrypt) ... else ...` + `ReplaceFile` branch verbatim). A migrated encrypted slot is therefore re-encrypted, never written as plaintext, and never left in a torn state (atomic tmp+replace preserved). Enforced by the must_haves prohibition + Task 4 acceptance criterion. This is the phase's only high-severity item (block_on = high) and is fully mitigated. |
| T-04-02 | Denial of Service / Deadlock | Load-time write-back re-entering the non-reentrant `_ioGate` | high | mitigate | Load/LoadAsync perform the write-back through the gate-held write core while already holding `_ioGate`, and NEVER call Save/SaveAsync (which would block on the same SemaphoreSlim(1,1) and permanently hang the slot). Enforced by the must_haves prohibition, the Task 4 grep assertion, and a non-hanging fixture-load test in Task 1. |
| T-04-03 | Data Loss | A newer app's save (future version) or a broken migration chain silently overwritten/truncated | high | mitigate | `DSMMigrationRunner.Migrate` throws `DSMSaveVersionException` on `fromVersion > CurrentVersion` or a broken chain; Load/LoadAsync let it propagate and do NOT write back or seed defaults, so the newer/unbridgeable file is left byte-for-byte intact for the caller to handle. Enforced by the future-version fixture test (asserts throw + bytes unchanged). |
| T-04-04 | Denial of Service | Malformed / hostile save JSON fed to the parser during migration | medium | mitigate | Parsing stays on Newtonsoft's `JObject.Parse`; a parse failure keeps the existing malformed->seed-defaults path (no crash). Migrations operate on the already-parsed JObject and evaluate no untrusted code. Deeply-nested-JSON resource pressure is bounded by the same parser the codebase already trusts for all loads — no new attack surface beyond the existing Load. |
| T-04-05 | Tampering | Version-field tampering (negative/zero/huge int, or a legacy key literally named `version`) | medium | mitigate | Non-integer or missing `version`/`data` -> treated as legacy v1 (TryUnwrap returns false); `fromVersion < 1` clamped to 1; huge/future int -> fail-closed DSMSaveVersionException (T-04-03). No code path sizes an allocation or loop bound from the attacker-controlled version. |
